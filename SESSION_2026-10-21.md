## 1. Performance da API — CONCLUÍDO (quase)
Causa raiz: N+1 (~3 queries/linha a ~130ms de ida ao TiDB) + contagens por `findByArea_Id().size()`.

Aplicado e compilado:
- `AreaArborizadaService.listar`: contagem agregada 1 query (`ArvoreRepository.contarPorAreaIds`, GROUP BY) + `countByArea_Id` para buscarPorId.
- **Revertido** os `@Query` com `JOIN FETCH` + paginação (Hibernate 7 gera subquery com alias de coluna `) ea1_0(col1,...)` sintaxe Oracle → `SQLSyntaxErrorException` no TiDB). Regra permanente: **não usar JOIN FETCH em coleção com Pageable**; usar `@BatchSize`.
- `@BatchSize` adicionado: `Arvore.fotos` (50), `EspecieArvore.fotos` (50) + classe (100), `AreaArborizada.fotos`/`pontos` (50) + classe (100). **Import = `org.hibernate.annotations.BatchSize` (NÃO existe em jakarta.persistence — erro em runtime se usar jakarta).**
- `CacheApiPublicaFilter` (novo, `config/`): cache em memória 30s p/ GET `/api/areas|/api/arvores|/api/especies` **sem cookie JSESSIONID**; salva corpo via wrapper, devolve no original com `setContentLength`. Operador logado nunca vê cache. (Só o header `Cache-Control: public, max-age=60` do `CacheControlPublicoFilter` não bastava.)
- Índices `@Table(indexes=...)`: arvores(area_id, especie_id), areas(nome), area_foto/arvore_foto/especie_foto FK.
- `spring.jpa.show-sql=false` (desligado de novo em `config/application-local.properties`).

Resultado medido (antes → depois):
- `/api/areas` 2100→**660ms** | `/api/arvores?size=500` 2600→**670ms** | `/api/especies` 3870→**520ms** (1ª chamada; repetidas vêm do cache ~instantâneo).

Pendente opcional: se quiser <300ms na 1ª chamada, só reduzindo round-trips (ex.: JOIN one-to-one de espécie/área) — mas JOIN FETCH em coleção está PROIBIDO (bug TiDB).
